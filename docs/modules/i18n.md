# Bilingual UI and taxonomy (i18n)

> English / Traditional Chinese (Hong Kong): a per-device UI-language cookie, a separate taxonomy-name cookie, an optional `name_zh` on subjects and every taxonomy level, a document heading language on the Generate page, and an in-house JSON catalogue shared by Jinja and JS. Decision: [ADR-017](../decisions/ADR-017-bilingual-ui-and-taxonomy.md).

UI language is **not** the paper version. Versions (`EN / CH / BI / ENO / CHO`, `app.utils.VERSIONS`) pick which file of a question to print; the UI language picks the words on screen. The only bridge is `heading_lang=auto` (below).

### What is translated (2026-10-17, about 3,900 keys)

Every teacher- and admin-facing page: navbar, login / register, dashboard (filters, cards, selection, Bulk Edit, Explain chat, presets), Generate and the viewer, My Files / Question Sets / Generation Profiles / Saved Filters / file browser / Admin Files, Toolbox hub, PDF Toolbox and Markup, the Edit Question modal (tag editor, MD editor, AI buttons), Question Management (`admin_questions/*`, split / combine / scope), Topics / Chapters / Subjects / Users / Restore Points / Subject AI, Smart Import, PDF Batch Import, Health, Export / Import, LLM Endpoints, AI Prompts (group, label, description), System Settings (group, label, help). Server side: flashes and route JSON `error` / `message` / `warning` in `admin.py`, `auth.py`, `dashboard.py`, `generator.py`, `files.py`, `files_service.py`, `user.py`, `pdf_import.py`, `question_*.py`, `restore_points.py`, `smart_import.py`, `subject_ai*.py`, `toolbox/pdf.py`, `ingestor.py`.

Bilingual-name consumers: `app/dashboard.py` (cards, `/dashboard/api/*` taxonomy APIs), `app/utils.py` (`GROUP_NAME_KEYS` → Generate reorder / grouping labels), `app/batch_edit.py`, `app/admin.py` (taxonomy CRUD, CSV, `_taxonomy_maps`), `app/ai_prompts.py` (`_taxonomy_block`), `app/ai_tools.py` (`_map_tag_names`), `app/subject_ai_service.py` (`taxonomy_tree`), `app/generator.py` (heading language), `templates/dashboard.html` + `partials/tag_editor_js.html` (search keys), `admin_topics.html` / `admin_chapters.html` / `partials/taxonomy_admin_js.html` / `admin_subjects.html` (editing).

## Tables

`name_zh` (nullable) on `subjects` (VARCHAR 100), `topics`, `subtopics`, `chapters`, `subchapters` (VARCHAR 200). `name` stays the English name and the sort / match key. Boot patch in `create_app()`; history in [../reference/schema-history.md](../reference/schema-history.md); tables in [../core/03-data-model-and-migrations.md](../core/03-data-model-and-migrations.md). `name_zh` is in the restore-point payload ([subject-snapshots.md](subject-snapshots.md)).

## Business rules / invariants

- **Two cookies, no DB:** `oqb_lang` = `en` | `zh` (default `en`); `oqb_tax_lang` = `en` | `zh` | `both` (default `en`). Per device, `path=/`, one year, `SameSite=Lax`. Unknown values read as the default. Set only by `OQB.setLang`, which reloads the page.
- **Catalogue keys are the exact English text**, placeholders `{name}` (Python `str.format` and `OQB.t` share the syntax). A missing key shows the English. Values must keep every placeholder of the key (`test_placeholders_match`).
- **Coverage:** `test_every_literal_is_translated` scans `templates/`, `app/`, `static/js/` for `t('…')`, `_t('…')`, `OQB.t('…')` whose first argument is one plain string literal, and fails on any key missing from the catalogue. JS template literals, concatenations and variables are invisible to it, so: one literal per call, values through params (`OQB.t('Created {qid}', {qid})`), and add keys for strings that only arrive at runtime (see `showToast` below, `validate_username` messages). `test_dynamic_keys_are_translated` covers text the UI passes through a variable: settings `REGISTRY` group / label / help, `PROMPTS_REGISTRY` group / label / description, `VERSION_LABELS`, `GROUP_NONE_LABELS`. A new registry rendered with `t(var)` / `OQB.t(var)` belongs in that test.
- **Keys have no context.** The same English text always gets the same Chinese, so short words were settled to fit every use (`Created` = 建立 for date columns and count badges; list in [glossary-zh.md](../reference/glossary-zh.md), "One key, one Chinese string"). When the meanings really differ, use a different English string.
- **State stays English; translate at display.** JS that branches on a status keeps the English value and maps it for the screen (`statusLabel()` / `stripStateLabel()` in `admin_pdf_import.html`, the restore-point label map in `admin_restore_points.html`). Server values compared in code stay English; the route translates at the edge (`subject_ai.py` translates the two fixed `ai_tools.build_tag_prompt` errors).
- **Python:** import as `from app.i18n import t as _t` in modules that use `t` as a loop variable (`utils`, `generator`, `admin`, `auth`). Outside a request `t` returns English.
- **Taxonomy display goes through one helper:** `display_name(node)` (Jinja `tax_name(node)`, JS `OQB.taxName(node)`), never `node.name` in teacher-facing text. Chinese mode falls back to English per node; Both prints `English 中文`, or just the English when the Chinese is blank or identical. Works on model rows, dicts and API nodes.
- **Matching never uses the display string alone:** `build_name_index(nodes)` keys every node by its English name, then its Chinese name, then `English 中文`, all lower-cased and whitespace-collapsed (`normalize_name`, which also strips a trailing `[中: …]`). An English name always wins a collision with another node's Chinese name. Stored references are ids; the tag-correction log and `display` of Auto Tag keep the **English** `name`.
- **Client search boxes** (dashboard filters, bulk-edit pickers, tag editor) search `OQB.taxSearchKey(node)` = the display label + English + Chinese, so typing either language finds a node whatever the display mode.
- **Documents never read a cookie.** `doc_lang(heading_lang, version_priority)`: an explicit `en` / `zh` / `both` wins; `auto` (or anything unknown) follows the first version: EN / ENO → `en`, CH / CHO → `zh`, BI → `both`, none → `en`. The background job puts the result in `label_opts['lang']`; section headings, the per-question info line, split file / zip entry names, the ANSWERS / SOLUTIONS / ANSWERS AND SOLUTIONS title, the `[Cross Topic: …]` note and the `Unknown` / `Uncategorized` split labels follow it (`doc_name`, `doc_label`). Section grouping keys are node **ids** (`_get_section_key`).
- **East Asian font:** the four OQB paragraph styles set `w:eastAsia = PMingLiU` (新細明體); Latin text keeps the theme font.
- **Auto Tag prompt:** `ai_prompts._taxonomy_block` lists a node with a Chinese name as `Name [中: 名稱]` and adds `TAXONOMY_ALIAS_NOTE` to the TOPICS / CHAPTERS header only when at least one visible node has one, so English-only subjects keep the exact old prompt.
- **`showToast` in `partials/edit_question_modal_js.html`** passes every message through `OQB.t`, so a message that is exactly a catalogue key (including fixed server `message` strings) shows translated. `window.confirm` text is wrapped explicitly.
- **Flask-Login's** "Please log in to access this page." goes through `localize_callback = i18n.t`.
- **Not translated by design:** progress logs, SSE lines (ingestion, sync, Smart Import apply, AI batch runs, asset operations, Explain / chat-console stream errors), AI prompt text and model replies, per-format proofread results, raw exception text in flashes (`flash(str(e))`), CSV column names, version codes, QIDs, placeholder examples such as `https://api.openai.com/v1`.

## Settings & config keys

None. Languages, defaults and the catalogue path are module constants in `app/i18n.py` (`UI_LANGS`, `TAX_MODES`, `HEADING_LANGS`, `DEFAULT_UI_LANG`, `DEFAULT_TAX_MODE`, `CATALOGUE_PATH`). See [../core/06-system-settings.md](../core/06-system-settings.md) if a default ever becomes a tunable.

## Permissions

The language switches are open to everyone, logged in or not. `/i18n/zh.js` has no login check. Editing `name_zh` follows the taxonomy routes: subject admin of the node's subject (`_require_subject_admin`), super admin for subjects ([admin-panel.md](admin-panel.md), [../core/02-auth-and-permissions.md](../core/02-auth-and-permissions.md)).

## Background work / SSE / threads

The catalogue is cached per process and re-read when the file's mtime changes (`_cache_lock`), so editing `zh_Hant.json` takes effect on the next request without a restart; the JS URL changes with the mtime. Generation threads receive the resolved language in `label_opts`; they have no request and must not call `t()` / `display_name()` without an explicit mode.

## Gotchas

- **Changing an English string orphans its translation.** The key is the English text; update `zh_Hant.json` in the same edit. The test catches new literals, not stale keys.
- **Do not concatenate translatable fragments** (`t('Imported') + ' ' + n + t(' files')`): word order differs in Chinese. Use one key with placeholders.
- **A Jinja variable named `t` shadows `t()`** for the rest of its block (`{% for t in types %}` breaks every later `{{ t('…') }}` with "str is not callable"). `admin_topics.html` renamed its loop variable to `qtype`.
- **Renaming a setting label, help text or prompt description orphans its translation** like any other key; `test_dynamic_keys_are_translated` reports the new English as missing.
- **Template tests assert the source, not the output.** `tests/test_generate_template_ux.py` looks for `{{ t('Answer lines') }}`; a test that greps a template for English text must match the wrapped call.
- **Translated pages still show English stream lines.** SSE progress (ingest, sync, AI batches) is English on purpose; do not wrap `yield {'message': …}` in `_t` (threads have no request, so it would be English anyway).
- **`OQB.t` needs `static/js/i18n.js`**, loaded in `<head>` of `base.html`, `viewer.html` and `markup.html`. A new standalone page (not extending `base.html`) must load both scripts itself.
- **`.tax-name-zh` spans must have no whitespace inside** (`{{ x.name_zh or '' }}` on one line): the "+ 中文名稱" placeholder uses `:empty::before`.
- **CSV import never renames the English name.** A row matched only by its `*_name_zh` cell keeps the existing English and adds a warning; a blank `*_name_zh` cell (or a missing column) leaves the Chinese alone, so clearing a Chinese name is done in the UI.
- **Duplicate Chinese names across nodes** resolve to whichever was indexed first; keep Chinese names unique within a subject like English ones.
- **Old tag corrections** quote the names that existed when they were saved (CHEM's packed `English 中文` names). Clear the subject's correction log after splitting names (AI Tagging Tuning → Teacher corrections report → bin button, `POST /admin/subjects/<subject_id>/ai/corrections/clear`).
- **Restore points from before 2026-10-17** have no `name_zh`; restoring one leaves Chinese names unchanged.
- **Generation runs in a thread:** pass a resolved `lang` (`label_opts['lang']`, `label_lang=`); `display_name()` without a mode would fall back to English there.
